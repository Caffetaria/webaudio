The Memory Palace Synth

The Memory Palace Synth is an interactive WebAudio piece where the user explores a virtual room through sound. Instead of playing notes on a keyboard or triggering samples from buttons, the user moves through a simple 2D space. Different objects in the room generate different sounds, and the user’s position determines how those sounds behave.

Project Overview

For my final project, I built The Memory Palace Synth, an interactive sound environment inspired by the idea of a memory palace. A memory palace is usually imagined as a mental room or building where memories are placed in specific locations. I wanted to translate that idea into sound: instead of walking through a room visually, the user explores the room by listening.

The project treats space as the instrument. The user is represented as a point in a 2D room, and different objects in the room act as sound sources. A window creates a shifting wind texture, a lamp produces a warm electronic tone, a desk generates small rhythmic clicks, and a hidden memory slowly reveals a deeper drone when the user stays near it. As the user moves closer to an object, that object becomes louder, brighter, and more present. As the user moves away, it becomes softer, darker, and more distant.

The result is somewhere between a synthesizer, a sound installation, and a small navigable world. The user is still performing, but the performance is based on movement rather than notes. This made the project a useful way to explore computational sound as an environment rather than only as an instrument.

Design Motivation

Most synthesizers give the user direct controls: keys, knobs, sliders, buttons, or pads. I wanted to design an interface where the user controls sound indirectly through position. Instead of saying “make this oscillator louder,” the user simply moves closer to an object. Instead of manually turning a filter knob, the user hears the sound become brighter as they approach.

This design choice made the interaction feel more natural and exploratory. The user does not need to understand the underlying synthesis parameters to use the piece. They can simply move through the room and learn how the space behaves by listening. At the same time, the implementation is still grounded in familiar WebAudio techniques: oscillators, gain nodes, filters, panning, envelopes, modulation, and parameter automation.

The main design idea is simple: the room is a control surface for sound.

System Architecture

The implementation is built around modular WebAudio signal chains. Each object in the room has its own sound module, and each sound module contains the nodes needed to synthesize and shape that object’s sound. The animation loop continuously updates the user’s position, calculates the distance to each object, and maps that distance to audio parameters.

User position ↓ Distance calculation ↓ Proximity mapping ↓ Object-specific WebAudio graph ↓ Master gain ↓ Audio output

This architecture helped keep the project organized. Rather than writing separate interaction logic for every object, I used a shared distance-based mapping system. Each sound object receives a proximity value between 0 and 1. The object can then interpret that proximity value in its own way. For one object, proximity might control volume and brightness. For another, it might control rhythm density or modulation depth.

This separation between spatial interaction and sound synthesis was one of the most important implementation decisions. It made the system easier to expand because new objects can be added without rewriting the entire interaction layer.

Sound Object Design

The room contains four main sound objects. Each one uses a different synthesis approach so that the room has multiple sonic layers: atmospheric, tonal, rhythmic, and hidden.

The Window: Filtered Noise

The window is based on filtered noise. A noise source is routed through a filter, and the filter frequency changes slowly over time. The goal was not to create a perfectly realistic wind simulation, but to suggest air, movement, and distance. When the user is far away, the window is quiet and dark. When the user moves closer, the filter opens and the sound becomes brighter and more detailed.

This object uses noise synthesis, a BiquadFilterNode, a GainNode, and slow modulation. It connects directly to class topics like filters, signal graphs, and LFO-style movement.

The Lamp: FM-Inspired Tone

The lamp creates a warm electronic tone. I designed it as an FM-inspired sound, where one oscillator acts as the carrier and another oscillator modulates the carrier’s frequency. A gain node controls the modulation depth. As the user moves closer to the lamp, the tone becomes stronger and the modulation becomes more noticeable.

I liked this design because the lamp feels like it is glowing sonically. It is not just a static pitch. It has a subtle internal movement that becomes clearer as the user approaches.

The Desk: Rhythmic Clicks

The desk produces small rhythmic clicks. These are created with short gain envelopes applied to simple waveforms. The events are scheduled repeatedly, but with slight timing variation so the rhythm does not feel completely mechanical.

This object adds a percussive layer to the room. It also gives the user a different kind of interaction: instead of only changing loudness or brightness, proximity can make the desk feel more active and rhythmically present.

The Hidden Memory: Accumulating Drone

The hidden memory is a slow drone that does not reveal itself immediately. It responds not only to where the user is, but also to how long the user stays there. If the user lingers near the hidden memory region, an internal memory value increases and the drone gradually fades in. If the user leaves, the drone fades away slowly rather than disappearing instantly.

This was my favorite part of the project conceptually. It connects the technical behavior of the system to the idea of memory. The sound is not simply triggered. It is uncovered over time.

Distance-Based Interaction

The core interaction system is based on distance. For each object, the program calculates the Euclidean distance between the user and the object. 

distance = Math.sqrt(
  (user.x - object.x) ** 2 +
  (user.y - object.y) ** 2
);

This distance is then converted into a proximity value. A simple version of the mapping looks like this: 

proximity = 1 - Math.min(distance / object.radius, 1);

This gives each object a radius of influence. If the user is outside the radius, the proximity is 0 and the object is mostly silent. If the user is at the center of the object, the proximity approaches 1 and the object becomes fully active.

I did not use proximity only for volume. That would make the interaction feel flat. Instead, proximity controls several parameters at once:

  • Gain: nearby objects become louder.
  • Filter cutoff: nearby objects become brighter.
  • Panning: objects move across the stereo field depending on their position.
  • Reverb or delay amount: distant objects can feel softer and farther away.
  • Modulation depth: some sounds become more animated as the user approaches.

This multi-parameter mapping creates a stronger sense of space than volume alone. In a real environment, distance changes more than loudness. Faraway sounds are often darker, less detailed, and more blended with the room. I wanted the synth to capture that feeling, even with a simple 2D interface and stereo output.

Why Procedural Sound?

A major design decision was to synthesize the sounds procedurally instead of relying on prerecorded samples. Samples would have made it easier to create recognizable sounds, but they would also make the piece feel more fixed. I wanted the room to feel alive and responsive.

Procedural sound gave me more control over how each object responds to movement. Because the sounds are generated in real time, their parameters can be continuously shaped by the user’s position. The window’s filter can open gradually. The lamp’s modulation depth can change smoothly. The desk’s rhythm can become more active. The hidden memory can accumulate over time.

This also made the project feel more connected to computational sound. The sounds are not static files being triggered. They are processes. They run, change, and respond while the user explores the room.

Memory Accumulation

The hidden memory object adds a second layer of interaction beyond simple proximity. Most objects respond immediately to distance: move closer and the sound becomes stronger; move away and it fades. The hidden memory instead uses accumulation.

When the user remains near the hidden region, a memory value slowly increases. That value controls the gain and richness of the drone. When the user leaves, the value decreases gradually. This means the sound has a kind of persistence. It remembers that the user was there. 

if (nearHiddenMemory) {
  memoryAmount = Math.min(memoryAmount + 0.01, 1);
} else {
  memoryAmount = Math.max(memoryAmount - 0.003, 0);
}

This mechanic made the room feel less like a set of buttons and more like an environment with behavior. It also gave the piece a small sense of discovery. A user might pass through the room and miss the hidden layer at first, but if they linger in the right place, the sound slowly appears.

Interface Design

The visual interface is intentionally simple. The room is shown as a 2D space with a user marker and several object markers. The user can move with the keyboard or mouse. I wanted the visuals to provide enough orientation without competing with the audio.

The most important feedback comes from listening. The interface shows where things are, but the user understands the space by hearing how the room changes. This kept the project focused on computational sound rather than becoming a complex visual game.

I also wanted the interaction to be understandable without a long explanation. The basic action is simple: move around and listen. Underneath that simplicity, the program continuously maps distance, position, and time to synthesis parameters.

Implementation Challenges

Smoothing Audio Parameters

One challenge was avoiding clicks and sudden jumps. Since the user’s position changes constantly, the audio parameters also change constantly. If gain or filter values are updated too abruptly, the sound can become glitchy. To avoid this, I used parameter smoothing and gradual ramps when changing values. 

gainNode.gain.linearRampToValueAtTime(
  targetGain,
  audioContext.currentTime + 0.05
);

Small smoothing times made the interaction feel responsive while still preventing harsh discontinuities.

Balancing the Mix

Another challenge was balancing multiple continuous sound sources. Since several objects can be active at once, the mix can quickly become too dense. I addressed this by giving each object a limited gain range and routing all objects through a master gain node.

I also designed each object to occupy a different sonic role. The window is noisy and atmospheric. The lamp is tonal. The desk is rhythmic. The hidden memory is slow and harmonic. This helped the layers combine without all competing for the same space.

Keeping the Interaction Simple

A final challenge was deciding how much control to expose. I could have added many sliders for every synthesis parameter, but that would have weakened the main idea of the project. The point was not to build a traditional synthesizer interface. The point was to make movement the main control mechanism.

I therefore kept the user interaction focused on navigation. The complexity lives inside the mapping system and sound modules, while the user experience remains simple.

Relationship to Computational Sound

The Memory Palace Synth draws from several topics in computational sound. At the DSP level, it uses oscillators, noise, filters, gain envelopes, modulation, panning, and signal graphs. At the interaction level, it uses spatialization and distance-based parameter mapping. At the compositional level, it creates a semi-generative environment where the final sound depends on the user’s path through the room.

The project also connects to automated composition. There is no fixed timeline that plays the same way every time. Instead, the room defines a set of musical possibilities, and the user’s movement determines which sounds appear, overlap, and evolve. The composition is partly designed by the system and partly performed by the user.

What I Would Add Next

If I continued developing The Memory Palace Synth, I would add a room editor. The user could place their own objects in the space and assign each object a sound type. This would turn the project from a fixed composition into a small spatial composition tool.

I would also like to explore more advanced spatial audio. The current version uses stereo panning and distance-based parameter changes, but it could be extended with binaural panning, convolution-based room simulation, or multichannel output.

Another possible extension would be a live-coding interface. The user could type commands to create or modify sound objects during performance. For example, they might add a bell object, change the memory drone intensity, or alter the radius of the window’s influence. This would connect the project more directly to the live coding module of the class.

Final Thoughts

The most successful part of the project is the way it turns space into a musical control surface. The user does not need to know music theory or synthesis terminology to interact with it. They can simply move through the room and discover how it sounds.

At the same time, the implementation is grounded in core WebAudio ideas. The piece uses signal graphs, modulation, filtering, gain control, envelopes, panning, and procedural synthesis. These techniques are not isolated exercises here; they work together as parts of a larger expressive system.

Overall, The Memory Palace Synth helped me think about computational sound as a way to build environments rather than only instruments. It is a room that remembers through sound, and the user composes by exploring it.
